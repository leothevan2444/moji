# 演员历史全量检查：设计提案

状态：未实现；2026-10-27 按 `86f69e5` 重新校准。原始产品方案日期为 2026-07-16。实施状态与下一步只在 [TODO F-001](../TODO.md#f-001) 维护。

当前没有 FullScanService、对应作业表、GraphQL 操作或 `PERFORMER_FULL_SCAN` 来源。手动检查未订阅演员已经可用，但仍执行现有增量发行检查，不能作为本功能完成证据。

## 保留的产品要求

- 为任意 Stash 演员显式启动一次历史检查，不要求已订阅，也不自动订阅；单演员和多选共用模型，最多 100 人。
- 完整枚举当前 StashBox 可列举的历史影片，不受订阅首次 240/后续 80 条窗口或自动下载日期范围限制。不承诺覆盖上游未收录作品。
- 每次确认保存不可变策略：单人始终尝试下载；多人、合集默认关闭，每次重新选择；未知分类跳过。
- “下载”表示创建标准 Moji 任务；不保证有可用资源，也不执行另一套寻源/下载流程。
- 已在 Stash、已有 Moji 任务和同一作业内重复场景跳过；共享多人影片跨演员最多创建一次。
- 后端持久作业，mutation 快速返回；可查看进度、分页结果、取消，浏览器刷新恢复显示，进程重启继续未完成工作。
- 取消保留已创建任务和结果，不回滚下载；一名演员失败可以继续后续演员，持久化失败则停止，不发布假成功。
- 不改变现有定时/增量检查，不给 `RefreshAll` 加 `full=true`；明确的单独操作与压力预算。

## 需要按当前架构实现的边界

| 领域 | 设计要求 |
| --- | --- |
| performer 专用服务 | 管理 job、演员、分页 cursor、策略、取消和结果；不建立通用作业框架 |
| metadata/registry | 按已配置 endpoint 和演员 stash ID 映射；不按名称弱匹配，不信任客户端元数据 |
| 分类 | 复用当前 subscription 的分类语义；若抽共享纯分类包，回归证明订阅语义不变 |
| taskflow | 增加明确 full-scan intent，并映射到独立来源；所有创建仍走 runtime 身份与番号去重 |
| storage | job、策略、cursor、scene claim、取消、结果和关键决定在 Manager 核心库，通过新迁移增加 |
| Web/GraphQL | 开始/取消 mutation，有界作业摘要/结果查询、进度更新与断线后快照恢复 |

旧方案“与任务共享 runtime 库、初始化时执行 performer schema”已过时。当前 runtime.db 是可替换观测，不能保存作业恢复真值；旧 per-domain schema 不是生产迁移入口。

旧方案还假设来源为开放 TEXT。当前 core `tasks.source` 有 CHECK，新增 `PERFORMER_FULL_SCAN` 必须用受支持迁移演进约束，并同步 Go、GraphQL enum、mapper、UI 与持久化回归；不能只加一个常量或修改已应用 core.sql。

## 枚举与去重

服务端逐页读取并处理，建议页大小 100，服从上游限制；不把全目录物化后才工作。只有上游无下一页、空页或可信 total 到达才可完成；重复页/无新 ID 识别为分页停滞失败，不能把内部上限触达当成功。

只有完整 cache generation 能代表完整枚举；不完整时继续加载。每页处理完成后才推进持久 cursor，恢复可重读最后一页。

场景先验证目标演员归属和稳定身份，再分类及策略过滤，然后校验番号、Stash 精确 stash ID/endpoint 匹配及规范化番号，最后经 taskflow 创建。策略明确排除的场景无需昂贵 Stash 查询。

job 内持久 claim 防止跨演员重复，taskflow 保证跨 job 去重。但 claim 不能提前永久吞掉崩溃时未创建的任务：实现前明确 `claimed → resolved/queued/skipped/failed` 和恢复协议。任务创建后结果保存失败，恢复必须关联原任务，而非仅因已 claim 就跳过。

`clientRequestId` 用于 start 幂等；同 ID 不同策略/演员输入需有明确冲突校验。job 创建与演员输入原子提交；结果、计数及 cursor 的提交边界必须能解释每个输入，不产生重复计数。

## 生命周期、并发和保留

作业 `QUEUED → RUNNING → COMPLETED/PARTIAL/FAILED/CANCELLED`；演员另有 SKIPPED，场景结果 `QUEUED/SKIPPED/FAILED`。`QUEUED` 结果只表示任务已创建。

第一版一个 worker、演员串行、场景逐项处理，不未经测量扩大并发。同演员活动冲突产生明确 skipped 结果，不把新策略合并到旧 job；其他演员继续。所有调用可取消，页前、场景前和外部返回后检查取消，接入应用 shutdown/join。

计划保留完成结果 30 天，活动作业不清理；关键授权、取消和任务关联按核心持久决定要求保留。实施时明确哪些明细可以过期、哪些事实不能随 job 删除；不能直接把“30 天结果保留”扩展成删除重要决定。

## UI 与契约

独立“历史全量检查”入口、策略确认、进度和分页结果，使用现有 Drawer/Modal 能力；检查操作遵循当前 `faBinoculars` 约定，名称与增量检查明确区分。原方案的旧图标不再作为实现要求。

状态来自持久 job，事件仅作加速；丢失、重连和重新打开读取快照。采用推送还是共享受控轮询，应在具体契约确定时说明，不能依赖浏览器长请求或前端串行抓全目录。

至少表达这些结果原因：已创建、Stash 已有、Moji 已有、作业内重复、多人/合集未启用、未知分类、缺番号、无演员映射、活动冲突、上游分页停滞、查询/创建失败、取消。用稳定代码本地化并携带 correlation ID，诊断不直接暴露给用户。

## 验收场景

1. 301 条、每页 40 条的 fixture 读取全部 8 页；重复页失败而非假完成，取消不再推进新场景。
2. 未订阅演员可启动且不变订阅；单人/多人/合集/未知严格遵守本次策略与现有分类，包括明确的 VR 处理边界。
3. Stash ID 或番号命中、已有各状态任务、多演员同片、重复 mutation、任务创建后崩溃均不重复创建或漏处理。
4. 重启继续 cursor、claim 与计数一致；取消不删已建任务；单演员失败不吞后续演员；持久化失败不执行未记录副作用。
5. 结果 store 层分页，有界内存与外部请求；UI 刷新、断线、跨页结果、部分失败及中英/移动/焦点行为覆盖。
6. 新 core 迁移、source CHECK、备份恢复、生命周期 join、定时检查不调用 full scan 均有回归。

实施前先补齐 claim/任务创建间的恢复协议和新来源迁移设计，再分持久化、执行、契约、Web 的可验证切片推进。这里不保留尚不存在的完整 SQL 或假定函数签名，避免未来实现被旧草图误导。
