# 订阅检查结果、历史重试与过程诊断

## 用户确认的行为

演员检查应重试历史发行的任务创建失败；本次目录检查与历史重试的失败应分开展示。检查记录要说明实际读取与处理结果，并让用户能定位影片、原因和下一步。沿用已确认的保护：人工拒绝、策略跳过不重新下载；临时故障自动退避，身份冲突和不完整元数据等待人工处理。

## 实现

- CheckItem.Status / Error 和演员 LastError 只反映本次检查自身的读取、持久化或中断结果；不再扫描历史失败并复制旧错误。新任务创建失败单独记录为发行结果。活跃度和检查调度继续按目录观测安排，不被旧错误污染。
- 手动演员检查立即尝试其历史 FAILED 记录，包含当前分页范围外的历史发行；定时检查只尝试到期的临时故障。每演员每次最多 32 项，延后数量明确显示。新产生的失败不会在同一次检查内再次尝试。
- 每次重试重新核验已有任务、Stash 影片关联、StashBox 完整影片与发行日期。原本自动下载的记录重新评估当前策略；需要复核或跳过时转为相应决定。已明确人工选择下载的决定保持其授权语义。任务仍经 taskflow 接收和身份去重。
- 临时故障按类型识别：期限、断连、EOF、暂时网络错误和 HTTP 408/429/500/502/503/504；不根据错误字符串猜测。退避为 1/5/15 分钟、1/6/24 小时，之后至多每日一次。次数与截止时间保存在现有发行 JSON 中，重启不重置。身份冲突、元数据缺失、认证失败和未知错误不安排后台重试。
- 现有每分钟待发行 worker 同时处理到期发行重试，每批最多 8 项、整个批次 2 分钟、单项 45 秒。遵守自动检查开关，重读决定，确认仍有订阅演员；取消订阅时暂停自动重试。与人工复核和演员检查使用相同的 reviewMu，拒绝或已接收任务不会被后台旧读取覆盖。持久化后发布现有订阅刷新事件。
- 每次检查保存版本化 CheckDetails：阶段、目录来源与模式、请求页数、返回条目、发行范围、停止翻页原因、本次发行处理统计、历史重试统计及逐影片结果。结果包含完整番号、标题、策略原因、错误代码、原始错误、任务 ID 和下次重试时间。最多保存 320 条结果，超出数量明确显示；每次完成的历史重试及其进度先持久化。
- 检查详情 UI 分为目录、发行、历史重试与可展开的逐影片记录。原始错误按需展开，提供任务和发行复核入口；影片入口查询所有当前状态，因此从旧检查也可找到已恢复影片。旧记录不补造明细；未执行阶段不显示为零条结果。HTTP 错误不保存响应正文，诊断原文有长度上限。

## 本地数据与实际验收

沿用本次任务已授权的人工数据库调整，不新增自动迁移或旧 schema 兼容分支。停止原 `go run` Moji 进程并保存其可执行文件；三份 SQLite 快照、归档、索引器文件、配置和旧程序备份于 `.storage/backups/check-details-20261115T144657Z`。验证 SQLite 完整性、外键及 1,757 个备份文件哈希。

在独立 `check-details-20261115T144657Z` generation 为 subscription_check_items 增加可空 details_json，人工对齐 core 基线 checksum，保留 31 张表的记录数量、任务身份及最近 100 次检查记录。旧记录保持空明细。新代码校验影片身份及检查记录后，通过 storage.PublishGeneration 切换并启动本地服务；旧 `film-tasks-20261115T100154Z` generation 保留。

对目标演员执行一次正式检查：目录读取 2 页、80 条记录，75 条已记录、5 条待发行；8 条历史失败全部尝试并成功接收任务，重试失败 0，检查及演员结果均 SUCCEEDED，LastError 为空。通过运行服务的只读 GraphQL 再次核对所有结果、策略原因及 8 个任务链接。私有运行 ID 和逐影片明细保存在 `.storage/check-diagnostics-recovery-*.json`。接收任务不等于已经完成下载或入库。
