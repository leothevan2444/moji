# Subscription check runs

Release checks have a persistent lifecycle distinct from the download tasks they may create. Both the scheduled worker and the Web UI use the same service, reservations, and history. Home combines subscriptions and checks in the My subscriptions card: subscription and latest-issue counts appear side by side, with management in the heading and a neutral History action at the right of the check-status row; idle status and the next relative deadline share the left side, while active actor/progress details replace that text during checks. The issue count links to `/performers?filter=error`, where users can inspect errors and check individual or selected actors. The latest finished scheduled result, recent result statistics and run history appear in the history drawer. Subscription counts and check state still load and recover independently.

`startSubscriptionCheck(ids: [ID!])` reserves and persists a run before returning its ID. Omit `ids` to check all subscriptions; an explicit empty list is rejected. Selected checks accept at most 100 distinct actors. Work runs under the application's lifetime with a 30-minute deadline, independently of the HTTP request. Closing or refreshing the browser does not cancel it.

`homeSubscriptionChecks` returns the schedule, full active count, at most three active and three recent run summaries, and the latest scheduled run. Each summary includes at most three currently checked actors. Its domain projection lives in `internal/subscription/home_checks.go`, its resolver in `home.resolvers.go`, and its frontend query in `home-page.graphql`. It reads local run state without upstream catalogue calls.

`subscriptionCheck(id: ID!)` loads full actor outcomes only when a Home drawer (`/?check=ID`) is opened. Actor controls use `subscriptionCheckActivity(ids: [ID!]!)`, which returns only reservations for visible and selected actors, the active count, and any all-actor reservation. It returns no history or full result records.

A run records its trigger (`MANUAL` or `SCHEDULED`), scope, timestamps, status, and individual actor outcomes. Actor outcomes describe this check's catalog and persistence work. Task creation failures are recorded separately, so an unresolved failure from an earlier check does not mark a successful catalog check as failed. Zero actors is a successful empty check once enumeration completes.

The detail drawer shows catalog source, incremental/initial mode, pages and entries read, the release processing range and pagination stop reason. It separately reports new release processing and historical retries, with film codes, policy decisions, errors, task links and scheduled retry times. Original errors are expandable. Older checks have no detailed observations; the UI states that explicitly instead of presenting invented zero counts. Stages that did not run are also shown explicitly.

A manual actor check immediately retries that actor's historical failed task admissions, including films outside the current catalog page range, up to 32 per actor per check. New failures are not retried again in the same check. Scheduled checks honor persisted retry deadlines. Every attempt revalidates library presence, existing task identity, current StashBox metadata and release date; automatic decisions also re-evaluate current policy. Rejections and policy skips are preserved.

Transient network/source failures use persisted delays of 1, 5, 15 minutes, then 1, 6 and 24 hours, capped at daily retries. The existing minute worker handles at most eight due retries per batch while Moji is running, and pauses retries for unsubscribed actors. Identity conflicts, missing metadata, authentication failures and unclassified errors require manual handling. Retry deadlines survive restarts. These release retries are independent of the actor's activity-based catalog check schedule.

Reservations cover the complete selected input for the lifetime of a run. An all-subscription run captures subscribed actors at admission and reserves the captured IDs before executing them. A repeated background request fully covered by an active run returns that existing run. Partially overlapping requests fail with `SUBSCRIPTION_CHECK_IN_PROGRESS`; disjoint selections can run concurrently. Older synchronous refresh mutations remain supported and participate in the same tracking and conflict checks.

SQLite retains the latest 100 runs, every active run, and the most recent scheduled run. Startup marks formerly running records and their unfinished actor items `INTERRUPTED`, with reason `SERVICE_RESTARTED`. Checks do not resume automatically after a restart; they can be triggered again or run at the next scheduled deadline. Ordinary shutdown and the overall deadline are also reported as interruption.

Automatic checks now use durable per-performer activity deadlines rather than a startup countdown. The worker wakes every five seconds and dispatches at most one due performer per 30 seconds, with at most one scheduled run active. Existing manual reservations defer only the affected performer. See [Performer activity and automatic checks](performer-activity.md) for the authoritative scoring, coverage, retry, and restart contract. Home shows active progress and offers recent results and statistics in an on-demand history window (up to 100 retained summaries).

Home and actor routes fetch their independent snapshots on mount and focus, every two seconds while checks are active, and every ten seconds while idle. Hidden tabs pause polling. Check buttons use the returned reservations; loading or failed status reads temporarily prevent a new submission. Active actor status links open that run on Home. Server-side reservations remain authoritative across tabs and concurrent requests. Existing performer subscription events continue to update actor results.

The Home subscription total and latest-issue count include only performers currently marked subscribed in Stash. A narrow ID/custom-field query establishes membership; local check-state projections supply outcomes without loading actor metadata, releases or StashBox catalogues. Each performer counts once. Failed/interrupted latest checks count as issues, successful checks clear them, and running checks retain the previous outcome. Historical task-creation retry failures remain separate. Membership-read failures preserve the last available UI values with an error instead of reporting zero.

The Home count and actor workspace reconcile their persisted check states with retained terminal run items using the same domain projection, including recovered interruptions. The ERROR actor filter requires current subscription membership before pagination; active checks keep the prior completed outcome.
